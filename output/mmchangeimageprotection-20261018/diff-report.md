# `MmChangeImageProtection` binary diff: 22621.4317 vs 26100.9022

Evidence is from the exact local PE instructions and matching PDB symbols in this directory: `22621-complete-disassembly.txt` (including the cold block), `22621-calls.tsv`, `26100-mmchange.asm`, `26100-mmchange-calls.json`, and the named callee disassemblies. The TLB section additionally uses `22621-mi-tb-flush-cdb-uf.txt`, `22621-ke-flush-tb-cdb-uf.txt`, `22621-ki-flush-worker-cdb-uf.txt`, `diff-26100-miset-full.asm`, `26100-full-22C9D0-MiFlushTbList.asm`, and `26100-complete-HvlFlushRangeListTb.asm`. All addresses below are **RVAs**. “Direct” means visible in those instructions; “inferred” marks a control-flow or semantic interpretation. No public documentation is used as behavior evidence.

## Function shape and checks

22621: hot extent `0x736CF0..0x736F9A`, with cold branches at `0x8C908E..0x8C912B`. 26100: contiguous `.pdata` extent `0xA62300..0xA62584`. The source registers remain `rcx` (object pointer), `rdx` (address), `r8` (length), and `r9d` (mode); both starts save `r9d` (`0x736CF5`, `0xA6230F`). Their visible predicates align as follows.

The **direct call set has changed**. 22621 explicitly calls `MmAcquireLoadLock` (`0x736D64`, `0x736EE1`), `ExAcquireResourceExclusiveLite` (`0x736D86`, `0x736EF7`), `MiLookupDataTableEntry` (`0x736D91`), `MiGetSystemRegionType` (`0x736DF9`), `MiSessionReferenceImage` (`0x8C909B`), and matching release/cleanup calls, including `MiUnloadSystemImage` (`0x736F1B`). 26100 instead enters `MiLockLoadedDataTableEntryIfNecessary` (`0xA62378` → `0x27C2D8`) and conditionally calls `MmUnlockLoadedDataTableEntry` (`0xA623FA` → `0x27BC50`). The new lock helper itself branches at `0x27C2EC..0x27C308` to `MiLockLoadedDataTableEntry` (`0x27C2FA`) or `MmFindDataTableEntryByAddress` (`0x27C308`); the unlock helper calls `MiUnlockLoaderEntry` (`0x27BC56`) and `MiReleaseLoadLock` (`0x27BC6B`). **Inferred:** this is a restructuring of module lookup/lock lifetime. The exact state equivalence of the two cleanup implementations is not established solely by the main-function call names.

Common direct callees remain `MI_IS_PHYSICAL_ADDRESS` (`0x736E35` → `0x25A7C0`; `0xA62476` → `0x2FE1B0`), `MiGetPagePrivilege` (`0x736E89` → `0x25A190`; `0xA624C1` → `0x299200`), `MiSetImageProtection` (`0x736EC2`/`0x736F8F` → `0x2EA3D8`; `0xA623A1`/`0xA623E4` → `0x2C59E0`), `MiClearPfnImageVerified` (`0x8C910E` → `0x3444CC`; `0xA6250E` → `0x32C4A0`), and `VslValidateDynamicCodePages` (`0x736F5F` → `0x879388`; `0xA6252B` → `0xA6258C`). The 22621 `MI_PFN_IS_PROTO` call (`0x736E72` → `0x2E9660`) is replaced by the inline sign test above. These changes are call-target or layout changes, not evidence of an added hash, signature, or caller-identity check in the main function.

## Mode-specific path comparison

Both versions first call `MiSetImageProtection` with `r9d=1` (`0x736EB5..0x736EC2`; `0xA62394..0xA623A1`), then compare the saved original mode to `1` (`0x736EC7`; `0xA623A6`). **Inferred from control flow:** mode `1` takes the validation/second-protection route; mode `2` takes the PFN verified-state clear/cleanup route. This is not a comparison against a caller-supplied `PAGE_READWRITE` or `PAGE_EXECUTE_READ` constant.

- **Mode 1:** both test MiFlags bit `0x4000` (`0x736F48..0x736F52`; `0xA623B1..0xA623BC`) and call `VslValidateDynamicCodePages` only when set (`0x736F5F`; `0xA6252B`). Both treat a negative return as failure (`0x736F66..0x736F68`; `0xA62532..0xA62534`). Both then call `MiSetImageProtection` again with `r9d=3` (`0x736F78..0x736F8F`; `0xA623CD..0xA623E4`), changing `r9d` to `0x13` when prior `ebx==0x12C` under MiFlags `0x8000` (`0x8C90CE..0x8C90DD`; `0xA62549..0xA62558`). The mode-1 VSL call and its status check are present in both versions.
- **Mode 2:** both test MiFlags bit `0x8000` before the per-PFN clear loop (`0x736ED1..0x736EDB` → cold `0x8C90E2..0x8C911B`; `0xA624D3..0xA6251B`). **Direct difference:** 22621 passes `edx=0x18` at `0x8C9109` to `MiClearPfnImageVerified` (`0x8C910E`); 26100 passes `edx=9` at `0xA62509` (`0xA6250E`). The loop is conditional on bit `0x8000` and a nonzero page count, not a mandatory action on every call.

## Security-sensitive lower calls

The mode-1 validation helper retains the same visible one-page limit and lock/secure-dispatch shape: 22621 `0x879420` `cmp rdx,1` / `0x879424` `ja` → invalid at `0x92BB14`; 26100 `0xA62624` `cmp rdx,1` / `0xA62628` `ja` → invalid at `0xA62733`. Both then call `MmProbeAndLockPages` (`0x87947C`; `0xA62680`), `VslpLockPagesForTransfer` (`0x87949B`; `0xA6269F`), `VslpEnterIumSecureMode` (`0x8794EA`; `0xA626EE`), and unlock. **Direct difference:** the immediate before secure dispatch changes from `edx=0x1F` (`0x8794D8`) to `edx=0x20` (`0xA626DC`). Its VTL1-side meaning and any internal verification result require a separate secure-kernel image; a changed operation number alone does not establish an added hash/signature check.

The mode-2 PFN helper changed the way it can alter protected-page privilege. In 22621, `MiClearPfnImageVerified` checks PFN type (`0x3444F0..0x3444F8`), tests `edx` flag bits `4` and `8` (`0x344510`, `0x34451D`), then conditionally reads privilege and calls `KeSetPagePrivilege` (`0x4C72B4`, `0x4C7315`) when its `MiGetPagePrivilege` result is nonzero (`0x4C72B9..0x4C72BB`). In 26100, the helper checks the same PFN type (`0x32C4B1..0x32C4C3`), tests flag bit `8` (`0x32C4F2`), then conditionally calls **one of** `VslRemoveProtectedPage` (`0x32C572` → `0x32C6F4`) or `VslMakeProtectedPageExecutable` (`0x32C5B2` → `0x32C774`) after `MiGetPagePrivilege` returns nonzero (`0x32C509..0x32C510`). The branch selection depends on privilege bits at `0x32C534..0x32C572`; neither VSL target is a guaranteed call on every mode-2 invocation. The 22621 `0x18` and 26100 `9` flags follow different branches inside their respective helpers, so their numeric values should not be treated as the same ABI enum.

`MiSetImageProtection` still forwards to `MiSetSystemCodeProtection` (`0x2EA410` → `0x258810`; `0x2C5A1D` → `0x2C5A30`). The 26100 wrapper explicitly writes a zero fifth stack argument at `0x2C5A15`. Its callee checks that slot at `0x2C5C1E`; only a **nonzero** value jumps to `MiRestrictSystemCodeProtection` (`0x2C6185..0x2C618B` → `0x4FD1E8`). On the observed `MmChangeImageProtection` route, the wrapper supplies zero, so this additional lower branch is **not** an added check exercised by either mode. Both versions have `MiMarkPfnVerified` in lower `MiSetSystemCodeProtection` paths (`22621` call `0x47E49C` → `0x2E24F4`; `26100` call `0x2C5B55` → `0x2C49D4`); it is not newly introduced in 26100.

## Observed TLB invalidation branches

Both lower protection implementations can reach `MiFlushTbList`: 22621 `MiSetSystemCodeProtection` calls it at `0x258B24`, `0x258B69`, and `0x258C19` (target `0x25E410`); the inspected 26100 implementation calls it at `0x2C5CF5`, `0x2C615E`, and `0x2C6173` (target `0x22C9D0`). The following are **branches visible in the respective local images**, not an assertion that every protection change executes all of them.

| 22621.4317 observed branch | 26100.9022 observed branch |
| --- | --- |
| `MiFlushTbList` `0x25E48B` calls `KeFlushTb` (`0x25E500`). `KeFlushTb` calls `KiFlushCurrentTbWorker` at `0x25E63C` and on an IPI route at `0x25E8D9`; the worker has `mov rax,cr3; mov cr3,rax` at `0x33154D..0x331550`, with another CR3 reload at `0x33159D..0x3315A0`. Its other branches call `HvlFlushRangeListTb` (`0x22D0A0`, `0x22D38A` → `0x22D620`), and IPI-related calls are also visible (`KiIpiSendRequest` at `0x22D20B`, `0x22D3E8`). |

The 26100 `HvlFlushRangeListTb` path has two concrete hypercall control constructions. At `0x22D7B9`, it writes `3` to the low dword of `[rsp+48h]`; `0x22D7D0` writes a bounded variable to the high dword, `0x22D7D4` loads the qword into `rbx`, and the conditional route `0x22D840..0x22D843` passes `rcx=rbx` to `HvcallInitiateHypercall` (`0x22E040`). Another branch writes low dword `3` at `0x22D8AC`, writes its variable high dword at `0x22D8B9`, ORs `0x10000` into the low dword at `0x22D90A`, then loads the qword into `rcx` at `0x22D916` for `HvcallFastExtended` at `0x22D925` (`0x22DAF0`). Thus the **low 32 control bits** are respectively `3` and `0x10003`; the full 64-bit `rcx` includes the variable high field and must not be reported as either literal. These are hypervisor-directed flush routes visible below the TLB helper. Their branch conditions matter; neither low control value is proven to be sent on every `MmChangeImageProtection` call. The old image excerpts establish the CR3/CR4 and IPI branches above; they do **not** establish the absence of `invlpg` or hypercalls elsewhere in 22621.

## Conclusion and coverage limit

**Directly visible:** the main-function input, range, PFN-form, privilege-bit, mode split, MiFlags gates, conditional VSL validation, and negative-status check have corresponding instructions in both builds. The direct loader/lock calls were reorganized, the PFN-form helper was inlined, the mode-2 PFN clear flags and lower protected-page privilege calls changed, and the mode-1 secure-dispatch immediate changed from `0x1F` to `0x20`. The inspected main and validator instruction lists do not show a newly added direct call named `Ci*`, `*Hash*`, `*Verify*`, or `*Validate*` beyond the VSL validation call already present in both.

**Not established:** equivalence of every cold branch within deeper PTE/prototype helpers, VTL1-side security policy or signature checks, and behavior for external callers. The old `MiSetSystemCodeProtection` includes a prototype-PTE route with `MiOffsetToProtos` at RVA `0x258C43`; the available 26100 first-200 callee excerpt does not provide a matched proof for that entire route, so no absence/newness conclusion is drawn there. Task 5 found no direct nt caller in either image and no named/ordinal import of this function in the local 26100 CI.dll, so no caller-supplied constant or RW→RX pair can be verified from those binaries.

CI import cross-check: the local 26100.9022 CI.dll has 262 named imports from ntoskrnl and **zero ordinal nt imports** (zero ordinal imports among all 278 imports). This strengthens the import-table observation in `xrefs-report.md`; it does not exclude a runtime-calculated or supplied function pointer.
