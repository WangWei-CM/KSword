# 不附加单步调试研究

研究日期：2026-10-17。源码核对基线：`b3f2eb32e5447f55a8927d7c05d3f45be2df561b` 及调研开始时的工作树。本文记录实现前的一手文档与旧实现核对；研究阶段没有加载新驱动、改变系统安全配置或运行调试目标。后续新增实现与运行证据另见 [内存调试模式](内存调试模式.md)。

## 结论

**不建立 Windows 调试附加关系，仍然真实执行单步，是可行的；但需要独立的异常/执行控制后端。** 对不协作的外部进程，已有研究路线是 hypervisor 调试器；对自有、主动协作的进程，可以由进程内异常处理器承担停止与单步。仅靠外部 R3 读写内存、反汇编和挂起/恢复，不能变成 x64dbg 式完整调试器。

上述基线的“内存调试”页属于不附加内存工作台，没有执行控制。旧 KSword HVM 调试断点最终仍向来宾注入 `#DB`，再由 Windows/Titan 调试事件循环持有停止；这一部分不能直接作为新的“不附加单步”实现。

近期可独立交付的部分是：线程暂停/恢复、线程选择、停止期间寄存器检查与 RIP 导航。必须称为“线程暂停与上下文检查”，并明确其线程范围；在独立停止事件消费者真正完成前，单步、步过、运行到地址及调试断点不能显示为可用。

## “不附加”的判定

本文将要求定义为：不调用 `DebugActiveProcess`，不以 `DEBUG_PROCESS` / `DEBUG_ONLY_THIS_PROCESS` 启动调试目标，不建立或借用 Windows Debug Object / debug port 的目标调试关系，也不依赖已有第三方调试器替本页接收停止事件。

“不附加”不表示目标不受影响，也不表示没有目标会话、无需权限或无法被观察到。暂停、改写寄存器和断点都会影响运行。本文不将透明性、规避反调试或隐藏 hypervisor 列为交付承诺。

Microsoft 将 `DebugActiveProcess` 定义为附加活动进程，并说明后续由 `WaitForDebugEvent` 接收状态与事件；x64dbg 的官方 `attach` 命令同样等待系统断点后交还控制。因此，继续使用这条事件循环而只替换内存、断点字节或 GUI 名称，不满足上述定义。[Microsoft DebugActiveProcess](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-debugactiveprocess)、[x64dbg AttachDebugger](https://help.x64dbg.com/en/latest/commands/debug-control/AttachDebugger.html)

## 一手研究与机制边界

| 机制 | 是否可无 Windows 调试附加 | 能力与限制 |
| --- | --- | --- |
| 普通外部 R3 内存会话 | 是 | 内存/反汇编、权限允许时暂停线程与读取上下文；没有自动获得异常事件消费权，不能单独完成通用真实单步。 |
| WinDbg/CDB noninvasive | 是 | 官方支持挂起目标线程、检查内存和寄存器；官方明确不能监控执行，`g` 等执行命令不可用。 |
| 目标主动集成 VEH | 是 | 目标自己的异常处理器可以获得异常上下文并恢复执行；可以设计真正的协作单步，但目标必须运行相应代码并保持通信。 |
| 独立 hypervisor 调试器 | 是 | 可在 Windows 调试设施之外截获执行、持有状态和单步；需要独立的线程/核心控制、事件协议与恢复机制。 |
| 转储/快照上的 CPU 仿真 | 是 | 在复制的 CPU/内存状态中逐条仿真；不等价于让原目标真实执行一条指令。 |

### 普通 R3 与 noninvasive 检查

Microsoft 的 noninvasive 文档明确区分“没有真正附加”和“能够控制执行”：前者成立，后者不成立。这是现成检查模式，不是现成的免附加单步接口。[Noninvasive Debugging](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/noninvasive-debugging--user-mode-)

`GetThreadContext` 可以作用于未被调试的线程，但运行中线程的上下文无效，调用者应先暂停线程。`SuspendThread` 增加暂停计数，`ResumeThread` 减少计数；暂停不选择精确指令位置，并可能让持锁线程停住。由此推导，KSword 可以实现受控线程检查，但需要逐线程记账，只归还本会话取得的暂停计数，不能循环恢复到零，也不能把枚举到的线程快照称为原子“全进程停止”。[GetThreadContext](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadcontext)、[SuspendThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-suspendthread)、[Suspending Thread Execution](https://learn.microsoft.com/en-us/windows/win32/procthread/suspending-thread-execution)

只执行“暂停 → 设置 TF → 恢复”还缺少下一次异常的接收、持有、上下文发布与继续处理。将 `INT3` 写入内存也只产生异常，不能自动产生一个由 KSword 持有的停止。异常消费者缺失时不得向普通运行目标试投这些操作。

### 目标主动协作的 VEH

Microsoft 允许应用注册 vectored exception handler 来观察/处理应用内异常；处理发生在调试器 first-chance 通知之后、栈展开之前。因此，无调试附加时可以由目标自己的处理器接管调试相关异常，但它不会自动成为另一个进程可用的外部异常订阅接口。[Vectored Exception Handling](https://learn.microsoft.com/en-us/windows/win32/debug/vectored-exception-handling)

工程上可以给自有测试程序或主动加载调试组件的目标定义协作协议：由组件发布当前线程的真实停止上下文，等待继续/单步请求，再把恢复结果发布给 KSword。这条路线不需要 Debug Object，但存在进程内组件，必须如实显示为“协作调试”；不能冒充“无需目标协作、无注入的任意进程调试”。官方 VEH 示例明确只适合 x86，不能原样用于 x64。[Using a Vectored Exception Handler](https://learn.microsoft.com/en-us/windows/win32/debug/using-a-vectored-exception-handler)

### HyperDbg：已有真正独立的执行控制研究

HyperDbg 官方用户态调试器设计说明，不使用 Windows debugging API，调试由 hypervisor 处理。其 VMI 用户态路线会进入 Thread Interception 阶段，只捕获尝试执行用户态指令的线程；停留在内核中的线程可能未被捕获，开始执行调试命令后也不会自动持续捕获新线程。[User-mode Debugger Principles](https://docs.hyperdbg.org/using-hyperdbg/user-mode-debugging/principles)

其命令仍叫 `.attach`，但文档明确暂停/拦截不使用 Windows API，由 hypervisor 完成。命令名称不能用来判断是否建立了 Windows Debug Object。相应页面同时警告用户态调试器仍为 beta、当前发行排除，并建议仅在受支持虚拟机中试验；不能把设计说明当成可直接投产的稳定 SDK。[HyperDbg .attach](https://docs.hyperdbg.org/commands/meta-commands/.attach)

两种单步还必须区分：`t` 使用目标 TF，其他线程/核心可以运行；`i` 使用 MTF，仅继续当前核并再次停止，其他核保持暂停，而且只适用于 Debugger Mode。`i` 可以跟随用户态到内核的异常与系统调用路径，因而不能简单理解成“目标线程下一条普通用户态指令”。[HyperDbg t](https://docs.hyperdbg.org/commands/debugging-commands/t)、[HyperDbg i](https://docs.hyperdbg.org/commands/debugging-commands/i)

全系统暂停的 Debugger Mode 要求另一台机器或虚拟串口控制；同一系统的 KSword Qt 界面不能在全系统停止时继续运行。VMI 用户态调试保留系统运行，是另一类控制模型，不能据此否定全部本地不附加调试路线。[Operation Modes](https://docs.hyperdbg.org/using-hyperdbg/prerequisites/operation-modes)

官方概览和 Build & Install 页面存在表述不一致：前者描述 VMI 用户态暂停/步进，后者仍笼统称本地 VMI 不能暂停或步进。当前应以具体用户态设计与 `.attach` 的 beta 限制理解能力；本次没有针对某个 HyperDbg 构建做运行确认，也没有验证其发布包是否实际启用该模块。[Attach to a Running Process](https://docs.hyperdbg.org/getting-started/attach-to-hyperdbg/attach-process)、[Build & Install](https://docs.hyperdbg.org/getting-started/build-and-install)

### Intel MTF 与仿真

Intel 定义 MTF 在特定指令边界产生 VM exit，而不是通用“目标线程已成功执行一条”的通知。事件投递、异常、其他 VM exit、`REP` 迭代等都影响边界。独立调试器必须证明停下的是哪个线程、哪个执行阶段，不能只用一次 MTF 计数加一作为单步成功证据。[Intel SDM：Monitor Trap Flag](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-vol-3c-part-3-manual.pdf)

Unicorn 官方将自身定位为 CPU 仿真框架，不处理完整机器与操作系统。因此它适合另列“快照仿真”，不能把仿真后的 RIP/寄存器写到界面上并宣称原目标已真实单步，尤其不能默认把仿真副作用回写目标。[Unicorn & QEMU](https://www.unicorn-engine.org/docs/beyond_qemu.html)

### 本地用户线程究竟停在哪里

这使 guest 内核、中断和调度仍有运行机会，也使本地控制界面有机会继续运行；目标线程下次尝试用户态取指时再次被拦截。它不等于操作系统认为线程已挂起，也不覆盖始终留在内核中的线程。反复 EPT exit 会产生开销，这是控制模型的直接推论；本次没有测量 CPU 占用、交互延迟或长时间稳定性。

### 当前单步不等于完全不改目标状态

当前用户态 `UdStepInstructions` 的 step-in 调用 `TracingRegularStepInInstruction`，后者设置 guest `RFLAGS.TF`。随后它关闭整个进程的拦截阶段，`ThreadHolderUnpauseAllThreadsInProcess` 清除全部已记账线程的 paused 状态。故源码支持的是“无 Windows 附加、通过 hypervisor 接收停止”，不能据此声称“MTF 单步、来宾 TF 不变、其他线程始终不动”。[UdStepInstructions](https://github.com/HyperDbg/HyperDbg/blob/ff3ba351a1059ce558967aa45a2c70ed25620aa4/hyperdbg/hyperkd/code/debugger/user-level/Ud.c#L303)、[TF 设置](https://github.com/HyperDbg/HyperDbg/blob/ff3ba351a1059ce558967aa45a2c70ed25620aa4/hyperdbg/hyperkd/code/debugger/meta-events/Tracing.c#L112)、[解除线程 paused 状态](https://github.com/HyperDbg/HyperDbg/blob/ff3ba351a1059ce558967aa45a2c70ed25620aa4/hyperdbg/hyperkd/code/debugger/user-level/ThreadHolder.c#L108)

step-over 遇到 call 时会在返回位置广播设置硬件调试寄存器；这也不是完全不改来宾调试状态的路径。[UdRegularStepOver](https://github.com/HyperDbg/HyperDbg/blob/ff3ba351a1059ce558967aa45a2c70ed25620aa4/hyperdbg/hyperkd/code/debugger/user-level/Ud.c#L227)

若需求同时要求“不注入、不改目标代码”和“不改变来宾调试寄存器/TF”，可以借鉴上述 MBEC 停驻模型，但不能直接包装其现有 `t/p` 实现作为满足条件的后端。新的 MTF 步进仍需补齐线程/换核归属、中断与异常边界、其他线程范围及恢复协议；仅新增能力位和禁用按钮不构成已实现这条路线。

### 能否直接接到内存调试 Tab

公开 `libhyperdbg` SDK 有命令执行、暂停/继续和单步导出，但此版本没有独立的 typed attach/结构化停止回调导出。文本回调可用于控制日志，不能作为当前停止身份与命令完成的权威证据。内部 `UdHandleUserDebuggerPausing` 才接收真实暂停包并更新活动会话。[SDK 导出](https://github.com/HyperDbg/HyperDbg/blob/ff3ba351a1059ce558967aa45a2c70ed25620aa4/hyperdbg/include/SDK/imports/user/HyperDbgLibImports.h#L119)、[暂停包消费者](https://github.com/HyperDbg/HyperDbg/blob/ff3ba351a1059ce558967aa45a2c70ed25620aa4/hyperdbg/libhyperdbg/code/debugger/user-level/user-listening.cpp#L29)

因此可试验的接入方向是独立 helper 配套启用 beta 的固定源码构建，并补充结构化事件/ACK，而非仅启动 CLI 后解析一行“successfully attached”。它仍需要自身 hypervisor，不能与现有 KSword HVM 争用 VMX 所有权。另一方向是在 KSword HVM 内独立实现上述控制模型，继续通过 `shared/driver/` 和 `ArkDriverClient/` 接入；这需要真实驱动实现和受控运行验收，当前没有可直接替换的一段稳定 SDK 调用。

以下描述改动前的源码基线，不覆盖后续新增的独立 VEH 与 HVM 协议，也不依据旧验收文档推定当前运行状态。

| 层次 | 基线入口 | 已有能力及缺口 |
| --- | --- | --- |
| 内存调试 Tab | `MemoryDock/MemoryDebugPage.cpp`、`MemoryDebugPage.h` | 独立内存会话，目标持续运行；明确没有暂停、单步与断点。复用正式 `MemoryWorkbenchView`，不是调试事件前端。 |
| 原生公共后端 | `DebuggerBackend/KswordDebuggerDebug.cpp` 的 `Backend::attach / waitEvent / continueEvent` | 分别调用 `DebugActiveProcess`、`WaitForDebugEvent`、`ContinueDebugEvent`。不能拿这组 API 作为新“不附加”执行通道。 |
| 借用前端会话 | 同文件 `observeNativeSession` | 原生前端拥有 debug port 与 pending event；“本后端不二次附加”不等于“目标无附加”。 |
| 驱动调试协议 | `shared/driver/KswordArkDebuggerIoctl.h`、`KswordArkHvmDebugIoctl.h` | 已有上下文、挂起、内存及 HVM 断点管理；HVM Debug v1 只有 Query/Add/Remove/Revoke，没有独立停止、单步、继续会话协议。 |
| HVM 命中 | `KswordARKDriver/src/features/hvm/hvm_debug.c` 的 `KswordARKHvmDebugInject` | 写 DR6 并向 guest 注入 vector 1，后续依赖来宾异常处理。 |
| HVM 退出 | `KswordARKDriver/src/features/hvm/hvm_exit.c` 的调试 MTF / EPT 命中分支 | 现有命中返回 guest `#DB` 路径；不是由新的不附加控制器持续持有 stopped target。 |

现有 `hvm_exit.h` 的出口为 Resume/Devirtualize/Fatal，退出分发契约不等待 GUI；不能在该路径加无限等待本机 IOCTL 的循环。现有 Freeze 的故障重试也不是调试停止会话。寄存器方面，VM-exit GPR 保存帧与 VMCS 的 RIP/RSP/RFLAGS 可以作为实现材料，但不能直接宣称完整 SIMD/XSTATE 停止快照已经具备。

源码路径中的 `MemoryDock/` 相对 `Ksword5.1/Ksword5.1/`。当前模式说明见 [内存调试模式](内存调试模式.md)，原生事件通道背景见 [x64dbg API 评估](ksword-x64dbg-api-review.md)。既有 [Continuous Watch 研究](next/hvm-continuous-watch-feasibility.md) 讨论的是连续监视的特定门槛，其历史 VM 缺 MTF 记录不能当成本次机器能力查询结果。

## 两条可行实现路线

### 路线 A：独立 HVM 执行后端

这条路线最接近用户希望的“外部目标、类似 x64dbg、真正不建立 Windows 附加”。可复用现有驱动访问门面、目标身份、内存读取与反汇编；停止与执行控制必须是独立会话，不能借用 Titan 已附加会话来补齐功能。

最小技术闭环应包含：

1. 版本化能力和会话协议，明确本地用户态或远程全系统模型、目标与线程身份、会话代次、停止事件序号及恢复所有权。
2. 真实的 Pending/Stopped/Running/Exited/Unsupported/RecoveryRequired 状态；停止上下文来自当前持有事件，历史 ring 只能显示历史。
3. 单步请求从一个真实停止出发，只有匹配目标、线程与请求代次的下一停止才完成；异常/退出/超时必须分别报告，不模拟成功。
4. 线程创建/退出、用户/内核切换、换核、模块和页映射变化，以及控制器退出时的有界恢复；不得依赖无限期阻塞当前系统来等待 Qt 发命令。
5. 断点范围和实际机制可查询；仅支持页粒度时就报告页粒度。缺少必要硬件能力时明确不可用，不能回退到 Windows 附加后仍保留“不附加”标签。

建议先在受控虚拟机完成“一个目标、一个工作线程、暂停 → 读上下文 → 执行一条 → 新停止 → 继续 → 清理”闭环，再扩展步过、运行到地址、断点与多线程。该顺序是实现建议，不是已经具备这些能力的声明。

### 路线 B：目标主动协作的 x64 VEH 后端

对于自有程序，可先提供显式集成的 x64 协作组件，建立窄通信接口和停止上下文协议，完成同样的单步闭环。它不需要 Windows Debug Object，也不要求内核/hypervisor；目标中的组件由程序主动加载或编译接入。

首期只支持受控目标、明确选定的协作线程与有限能力。异常归属、嵌套/无关异常、断点恢复、线程退出、前端断线、超时释放及原有异常处理链必须保留。若外部进程没有组件，应显示“不支持协作调试”，不能自动注入、偷偷改成原生附加或声称已完成通用不附加调试。

这条路线适合尽早验证 Tab 的会话状态、寄存器/反汇编联动和真实单步交互；若最终要求无目标内组件，路线 B 不能代替路线 A。

## 交付与验收门槛

源码与协议检查只证明实现路径和状态约束；构建成功只证明产物生成。以下运行证据必须另行取得：

- 受控目标运行前、停止时及退出后，均确认没有新建或借用 Windows 调试附加关系；不能只检查一个 API 是否出现于调用日志。
- 使用已知控制流的真实 x64 指令序列，对每次请求核对目标身份、TID、RIP、寄存器和可观察内存副作用；分支、调用/返回与异常分别验证。
- 核对其他线程是否仍可执行、停止范围与 UI 声明一致；覆盖换核、线程退出、PID/TID 重用、新线程和前端异常退出恢复。
- 原生暂停/恢复只归还本会话的暂停所有权；退出/取消后目标不因残留计数、TF、断点或等待通道持续停住。
- 实际主程序完成深浅主题、窄窗、长文本和动作可用性验收。专业工作台保留原内部布局，新增工具行复用共享入口。

本文完成研究和初始源码边界核对。后续已新增 R3 线程检查、目标主动接入的 VEH 组件及实验 MBEC/MTF 后端；准确构建和运行结果由 [内存调试模式](内存调试模式.md) 与组件 README 分别记录。本文的一手机制证据和既有带原生调试附加的 HVM 验收，均不能替代新后端的硬件运行验收。

## 2026-10-17 独立 HVM 后端实现与本地验证

本次已加入独立 `hvm_noattach` 执行后端和唯一 `HVM_NOATTACH` 协议，并通过 `ArkHvmNoAttachClient` 接入。它不借用原生调试事件循环：用户取指停点和匹配的 MTF 边界发布当前 GPR/VMCS 快照，`sessionId` 与可单次消费的 `stopId` 区分会话和停止身份。它没有调用 Windows 调试附加、注入 `#DB`、修改 guest TF/DR 或写入目标代码。该描述来自源码核对，实际虚拟化运行尚未验收。

首版只覆盖 **Intel MBEC + MTF、native x64 目标的一个明确选定用户线程**。其他线程和内核继续运行；暂停期间整个系统的用户/内核执行转换会增加 EPT exit，尚无性能测量。目标身份以持引用的 ETHREAD 直接比较，TEB 与 guest CPL 只作额外核对；线程退出通知先撤销 publication，不能以 ETHREAD 引用延长 TEB 寿命。根模式只允许 `KeGetCurrentThread` 这个当前线程身份 leaf，其余身份解析、分配、等待和框架操作均留在普通内核路径。既有 VMCS 设置在每个处理器的内核 IPI 上捕获该处理器的 kernel GS，并将它用于 HOST_GS_BASE；这是此身份读取的实现前提，不是 Microsoft 对任意 Windows API 在 VMX root 中可用的承诺。[KeGetCurrentThread](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-kegetcurrentthread)

三个预分配根共享原有下层物理映射：Normal 允许普通执行，UserGate 拒绝用户执行，KernelGate 拒绝 supervisor 执行。非目标用户取指与随后的内核入口切换门禁，因而不依赖猜测 KPTI 的另一份 CR3，也不需要在 MTF 后为下一 RIP 动态分配/切分 EPT 页。单步遇到中断、异常投递、其他 VM exit 或不匹配线程时明确中断，不伪报成功。重复停止和实际 STEP/CONTINUE 放行前都复核现场；改变后的上下文产生新的 FETCH 停止。CONTINUE_PENDING 也必须经过真实目标取指复核才转为 Running。

QUERY 不准备或启动 HVM；只有显式确认的 OPEN 才取得独占生命周期，依次执行准备、既有逐核自检、MBEC 根构造和全核插入。外部已经准备或常驻的 HVM 明确拒绝，不自动 STOP/TEARDOWN。预约期间其他策略修改也拒绝；Close、控制文件 Cleanup、owner/目标退出和电源退出撤销停止权。通用故障反虚拟化入口同步以原子操作撤销旧 STOPPED；全部处理器退出及页台账释放确认以后才放弃资源和对象引用。关闭失败保留 sessionId/RecoveryRequired 供恢复。
