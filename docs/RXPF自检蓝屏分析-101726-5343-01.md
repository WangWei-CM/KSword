# RXPF 自检安装 IDT 时的蓝屏分析

`dist/101726-5343-01.dmp` 的直接崩溃原因已经定位：RXPF 自检安装影子 IDT 时，`KswRxpfInstallIpi` 中的 `LIDT` 引发一般保护异常，Windows 将异常报告为 `STATUS_PRIVILEGED_INSTRUCTION`，最终产生 `SYSTEM_SERVICE_EXCEPTION (0x3B)`。安装结果检查与失败回滚位于 IPI 正常返回之后，本次异常没有沿正常的 NTSTATUS 返回路径恢复。

## 停止码与故障指令

```text
BugCheck 3B
Arg1 = 00000000c0000096
Arg2 = fffff8079775ef0e
Arg3 = ffffb3009f8ee900
Arg4 = 0000000000000000

KswordARK!KswRxpfInstallIpi+0x7e
fffff807`9775ef0e 420f015c020a  lidt tbyte ptr [rdx+r8+0Ah]
```

微软对 [0x3B 参数](https://learn.microsoft.com/windows-hardware/drivers/debugger/bug-check-0x3b--system-service-exception)的定义中，Arg1 是异常码，Arg2 是异常指令地址，Arg3 是异常上下文。对本转储执行 `.cxr` 恢复 Arg3 后，RIP 与 Arg2 完全一致；CDB `!error c0000096` 返回 `Privileged instruction`，异常栈包含 `nt!KiGeneralProtectionFault`。

源码对应 `KswordARKDriver/src/features/rxpf/page_fault_manager.c:335`：

```c
__lidt(&cpu->ShadowIdtr);
```

异常上下文的 `CS=0x10` 表明故障发生在内核态。调试器记录 CPU 1 的保存 IRQL 为 `0xE (IPI_LEVEL)`。

## 调用链与影响

CPU 1 的异常上下文栈能够可靠展开到下列链路：

```text
KswordARKDriverDispatchDeviceControl
  KswordARKRxpfIoctlRunSelfTest
    KswRxpfIoctlDispatchFixed
      KswRxpfRuntimeRunSelfTest          rxpf_runtime.c:733
        KswRxpfPageFaultInstall         page_fault_manager.c:531
          nt!KeIpiGenericCall
            KswRxpfInstallIpi           page_fault_manager.c:335
              nt!KiGeneralProtectionFault
                异常分发和系统服务异常处理
                  nt!KeBugCheckEx       0x3B / C0000096
```

调用返回地址的行号可能显示 `page_fault_manager.c:532`，实际发起 IPI 的语句位于 531 行。CPU 0 的保存栈也在 `KswRxpfInstallIpi+0x7e` 发生一般保护异常，调用者为 `nt!KiIpiGenericCallTarget`；其栈中的 BugCheck 请求参数为 `0x1E / C0000096`。转储头最终记录的是 CPU 1 的 `0x3B`。两条处理器栈共同支持同一次广播安装在多个 CPU 上触发指令异常。

`Ksword5.1.exe` 是发起自检请求的进程上下文，故障指令属于 `KswordARK.sys`。本次已经到达驱动自检执行入口；此前用户日志中的注册 IOCTL `Win32=998` 发生于更早阶段，不能用这份转储把两次失败直接归为同一故障。

## 结合源码的失败边界

| 源码位置 | 本次可以确定的状态 |
| --- | --- |
| `page_fault_manager.c:318-334` | 当前 CPU 已通过索引、Active 和原 IDTR 一致性检查，随后执行到 LIDT。 |
| `page_fault_manager.c:335` | LIDT 引发异常，未正常完成。 |
| `page_fault_manager.c:336-347` | 本次调用尚未执行 Installed 发布、安装后 SIDT 回读和最终成功返回。 |
| `page_fault_manager.c:531-546` | 逐 CPU 结果扫描依赖 KeIpiGenericCall 正常返回；本次停在回调内。 |
| `page_fault_manager.c:547-562` | 正常失败分支的恢复广播和验证尚未执行，不能声明已完成回滚。 |
| `rxpf_runtime.c:733-747` | 自检在安装阶段崩溃，尚未到本次安装后的启用发布和并发执行测试。 |

另一个状态解释边界是 `page_fault_manager.c:287`：准备阶段已经给每行 `LastStatus` 写入 `STATUS_SUCCESS`，单独观察此值不能证明 LIDT 成功。故障点周围没有局部异常处理；现有失败逻辑处理的是正常返回的错误状态，未能把这次 IPI 回调中的处理器异常转化为可控失败。

故障源码文件与 HEAD 一致，其分析时 SHA256 为 `750A476FB4A4E2458EFD3194B0F9E78B7F6566E8D70D717A654015B8A3FE4EF9`。`rxpf_runtime.c` 分析时 SHA256 为 `7055537473DAE9086BA1373466F7F6D4BED538329E9F00ADBC62AE7636F8E331`。仓库其他未提交改动不纳入这些文件已经修复或验证的结论。

## 平台归因范围与处置方向

转储记录 `AnyHypervisorPresent=1`、`IsHyperV=1`、`VsmAvailable=1` 和 `Nested=1`。它们说明存在 Hyper-V/VSM 能力及嵌套虚拟化相关状态；`VsmAvailable` 不等于 HVCI 已启用。这份小转储没有足够信息判定是具体哪项虚拟化策略或指令准入条件造成 LIDT 的一般保护异常。

可以确认的程序缺陷是：该实验路径在当前运行环境执行替换 IDTR 的操作并触发致命异常，现有前置检查及事后回滚不能保证这一操作安全失败。稳定性处置应先停止触发该构建的 RXPF 自检和 IDT 安装入口，在支持性得到验证前将该能力置为不可用，保留只读诊断并保持系统保护。本文不提供继续执行保护绕过的实现方案。

本次只读分析，没有加载驱动、复现蓝屏、修改产品代码或构建。原始转储保持不变。核对命令包括 `!analyze -v`、`.cxr`、`kv`、`!error`、`!lmi`、`!irql` 及逐 CPU 栈查看。

本地分析产物位于 `output/bsod-101726-5343-01/`：`cdb-final.txt` 为补齐符号后的完整输出，`identity-local.json` 为本地产物身份，`nt-symbol-identity.json` 为 Windows 内核符号身份。该目录中的转储衍生信息、公共符号与二进制不随本文提交。
